# 🔧 CONTINUOUS IMPROVEMENT SOP

> **Sub-SOP of the [Universal Prime SOP](../UNIVERSAL-PRIME-SOP.md).** The routine system-betterment operation — Stage 7.

**Purpose:** A system that doesn't examine itself decays. This is its own standing operation, run **routinely**, not an afterthought bolted onto the end of a task.

**Owned by:** 🔧 Updater/Optimizer Agent

---

## 1. WHEN IT RUNS

| Trigger | Scope |
| :------ | :---- |
| **End of every output** | Light pass — bottlenecks and opportunities noticed during this work |
| **After any systemic failure** | Full root-cause pass |
| **On request** | Full audit |
| **Routine interval** | Full system review |

---

## 2. THE IMPROVEMENT PASS

Each cycle asks:

| # | Question |
| :-: | :------- |
| 1 | **What slowed us down?** — bottlenecks |
| 2 | **What nearly broke?** — fragility and breaking points |
| 3 | **What was repeated?** — anything done more than twice should be systematized |
| 4 | **What was dropped?** — requirements lost, and *why* |
| 5 | **What was unclear?** — friction in communication or documentation |
| 6 | **What could be better?** — growth, enhancement, refinement opportunities |

Each finding is logged with **reasoning**: why it helps, and what it costs to not do it.

---

## 3. ROOT-CAUSE PROTOCOL (for systemic failures)

When a requirement is given, acknowledged, and then lost — the signature systemic failure — do **not** simply apologize and re-commit. That has already failed repeatedly.

| Step | Requirement |
| :--: | :---------- |
| 1 | **Identify WHY exactly** it keeps happening — the mechanism, not the symptom |
| 2 | **Name the agent** that should have caught it and why it didn't |
| 3 | **Implement an EFFECTIVE solution** — a structural change, not an intention |
| 4 | **Physically manifest it** into an easily referenceable, usable document |
| 5 | **Present it to the user** with a viewable link |
| 6 | **TEST it** — prove the fix actually works |
| 7 | **Log it** in the [Operations SOP](03-OPERATIONS-SOP.md) failure log with a timestamp |

> Steps 4–6 are what separate a real fix from a promise. A solution that isn't materialized and tested has not been implemented.

### Known recurring failure — worked example

| Field | |
| :---- | :-- |
| **Failure** | Token/time reporting requested, implemented, then silently dropped across sessions |
| **Why** | It lived only as an intention, not as a structural checklist gate |
| **Fix** | Added as a **standing item** in the [User Prompt Checklist](04-USER-PROMPT-CHECKLIST.md) §5 and a mandatory closing element in the [Communications SOP](02-COMMUNICATIONS-SOP.md) §2 — checked every output regardless of prompt |
| **Test** | Coherence Agent verifies presence at closeout; absence blocks the output |

## 4. THE OPTIMIZATION CYCLE (user-facing)

After the user confirms any deliverable:

```
OPTIMIZATION CYCLE — Round [#]

  1. [Suggestion] — why it helps, what not doing it costs
  2. [Suggestion] — why it helps, what not doing it costs
  3. [Suggestion] — why it helps, what not doing it costs

Confirm, adjust, or reject each.
```

| Step | |
| :--: | :-- |
| 1 | Provide specific improvement suggestions **with reasoning** |
| 2 | User confirms / adjusts / rejects **each** |
| 3 | Incorporate and present the updated version |
| 4 | **Repeat 1–3** until the user confirms no further improvements |
| 5 | **Only then** advance — present next-step options and let the user pick |

This cycle applies to **everything**. No exceptions.

## 6. THE STANDING PRINCIPLE

> Constantly identify bottlenecks and opportunities for growth, improvement, enhancement, refining, and bettering the system quality.

This is **routine**. The system gets measurably better every cycle, or the improvement operation itself is the thing that needs fixing.
